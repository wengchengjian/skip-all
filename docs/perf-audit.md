# 性能审计

对象：整个仓库的每帧热路径。基线数字见 [perf-baseline.md](perf-baseline.md)，
由 `scripts/perf_baseline.ps1` 在同一台机器上生成。

## 方法

1. 先建可复现基线：每个阶段单独计时，并统计每次调用的分配字节与**分配次数**。
2. 分配次数比字节数更重要：字节多只是堆大，次数多才是 GC 压力的来源。
3. 单帧重复测不够——换成**真实截图序列回放**，能暴露"几十帧才跑一次"的开销。
4. 每项改动用同一脚本复测，看同机前后差。
5. **被数据否决的想法也记下来**，否则下次还会有人再试一遍。

## 一帧到底花在哪

同机（i7-13700K）实测。先把一段完整帧拆成"截图 + 识别 + 决策"三段：

| 段 | 耗时 | 说明 |
| --- | ---: | --- |
| 截图（PrintWindow 为主） | **13 ms** | 2080x1210 窗口，见下 |
| 识别（OCR + 模板匹配） | 0~45 ms | 取决于本帧是否命中缓存 |
| 决策（颜色/文字行/状态机） | 0.1~2.2 ms | 见下 |

**截图是唯一"每帧必付且无法优化"的一段**，也是整条管线的地板。

### 截图路径拆分

对着本机真实窗口量（chrome 2080x1210）：

| 阶段 | 耗时 | 占比 |
| --- | ---: | ---: |
| PrintWindow | 12.7 ms | 97% |
| BitBlt（回退，正常不触发） | 13.1 ms | — |
| 缩放 + BGRA→RGBA | 1.0 ms | 7% |
| 合计（池化路径） | 13.0 ms | 100% |

PrintWindow 有一个很大的固定开销，与窗口大小关系不大：1011x666 的窗口
也要 6.5ms，1x1 的窗口也要 5.95ms。剩下的部分随窗口内容/尺寸增长。

缩放这一项之前是 31.5ms（1440p），已经优化到 1~2ms，现在只占 7%。
**真正的地板是 PrintWindow 这个 Win32 调用本身。**

想再往下只有换截图方式（DXGI Desktop Duplication），代价是失去后台截图能力
（DXGI 只能截前台），与项目"默认后台、不抢焦点"的定位冲突，暂不采用。

同机（i7-13700K）实测，1920x1080，38 张真实截图连续回放（每帧换图）：

| 功能 | 每帧 mean | p50 | p95 | OCR 次数/耗时 | 模板次数/耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| story_skip | 12.5 ms | 8.5 ms | 30.6 ms | 4 / 135 ms | 324 / 88 ms |
| auto_combat | 32.9 ms | 11.5 ms | 144.9 ms | 17 / 896 ms | 451 / 269 ms |

稳态（同一帧反复跑，缓存全命中）则低得多：

| 场景 | 每帧 |
| --- | ---: |
| 自动战斗，画面无 Boss 血条 | 2.22 ms |
| 自动战斗，画面有 Boss 血条 | 0.083 ms |
| 剧情跳过 | 0.22 ms |

结论：**OCR 与模板匹配两者合计占掉几乎全部时间**。稳态下剩下的 2.22ms
里有 1.9ms 是全屏颜色扫描，已经通过调整判据顺序消掉（见下）。

注意回放每帧换图，按帧缓存几乎不命中，因此比真实运行更悲观。

## 已修复

### 1. 逐像素接口装箱（pkg/vision）

`image.Image.At()` 每次返回 `color.Color` 接口。对 `*image.RGBA` 来说，
4 字节的 `color.RGBA` 会被装箱到堆上——**每个像素一次分配**。

| 文件 | 函数 | 修前每次分配 |
| --- | --- | ---: |
| color.go | analyzeColorWith | 330,000 次 / 1.3 MB |
| textbands.go | FindTextBands | 161,202 次 / 630 KB |
| template.go | WhiteMask / grayValueAt | 22,306 次 / 303 KB |
| color.go | filterByColorRange | 随区域像素数 |

修法：`pkg/vision/pixel.go` 的 `pixelReader`，对 `*image.RGBA` 直接读 Pix。

| 阶段 | 修前 | 修后 |
| --- | --- | --- |
| vision.colorstats | 6.22 ms / 330,000 次 | 2.71 ms / 0 次 |
| vision.textbands | 1.44 ms / 161,202 次 | 0.35 ms / 2 次 |
| feature.story_skip.step | 0.94 ms / 97,174 次 | 0.21 ms / 4 次 |

### 2. 模板匹配改用列和滑动窗口

`MatchTemplate` 原先对每个候选位置重算三项累加，内层每点还有一次下标乘法。
85 个内置模板里只有 1 个带掩码，所以无掩码是主路径：此时 `sumI`/`sumI2`
就是矩形窗口和，可以用列和滑动窗口 O(1) 推进，内层只剩 `sumIT` 一项。
另加一条：窗口方差过小时（纯色背景）直接跳过，省掉整趟 `sumIT`。

| 指标 | 修前 | 修后 |
| --- | ---: | ---: |
| vision.template_match（合成 48x48） | 16.75 ms | 7.97 ms（2.1x） |
| story_skip 模板总耗时 | 224 ms | 88 ms（-61%） |
| auto_combat 模板总耗时 | 485 ms | 269 ms（-45%） |

正确性：`TestMatchTemplateEquivalence` 用 24 个随机画面逐例对照优化前的
朴素实现，位置完全一致、置信度差 < 1e-9。

### 3. 战斗判定先查 Boss 血条（pkg/assist/combat）

`inCombat` 原本先查通用血条（整屏 200 万像素，约 1.9ms）再查 Boss 血条
（632x71 小矩形，约 0.04ms）。两者是"或"关系，顺序不影响结论，但代价差
两个数量级。改成先查 Boss，有 Boss 时直接短路。

| 场景 | 修前 | 修后 |
| --- | ---: | ---: |
| 带 Boss 血条的稳态帧 | 2.65 ms | **0.083 ms**（32x） |
| 无 Boss 血条的稳态帧 | 2.22 ms | 2.22 ms（无回归） |

## 已否决（有数据，别再试）

### 跳过 OCR 的文字检测（det）

det 占单次识别耗时的 60~80%（技能区 68x57：det 8.85ms / rec 2.66ms），
看起来"已知只有一行字的区域可以不做 det"。实现了 `RunRecOnly` 并在
38 张真实截图上逐组对照 det+rec 与 rec-only：

| 区域 | 一致率 | 耗时比 |
| --- | ---: | ---: |
| 技能区 1（68x57） | 23.7% | 4.4x |
| 技能区 2（68x57） | 28.9% | 4.0x |
| 技能区 3（68x57） | 39.5% | 4.0x |
| 确认对话框（550x140） | 23.7% | 5.8x |
| 对话内容（960x155） | 34.2% | 2.2x |

速度确实快 2~6 倍，但一致率只有 24~40%，典型差异如 `"200" vs "1"`、
`"7" vs "3"`。原因是 det 不只是"找框"——它还会把文字裁紧、按行归一化，
rec 依赖这个规整输入。直接喂整块区域（含图标、留白、多行）会乱读。

**结论：这条路对当前所有区域都不成立，代码已回退。**

### 给 Service.Template 加按帧缓存

照 OCR 缓存的做法加了一套。回放实测模板总耗时反而从 224ms 升到 251ms——
每帧换图时帧内没有重复调用，只多付了一次像素校验和。已回退。

## 待办（按影响排序）

### A. OCR 每次调用分配 5.4 MB / 2,736 次

全部发生在 `third_party/go-ocr`：`preprocessDetImage` 7.2MB、
`draw.CatmullRom` 临时缓冲 3.1MB、`postprocessHeatmap` 2MB。
该库是本地 replace 的 fork，可以改，但要同步更新 NOTICE 与 docs/upstream.md。
收益是降低 GC 压力，不改变耗时。

### B. 模板调用次数偏多

auto_combat 每帧 11.9 次模板匹配、story_skip 每帧 8.5 次。
目前靠算法提速扛住了；要进一步降只能减少调用次数（缓存识别结果、
收窄判据触发频率），都会改变行为，需要单独评估。

### C. 全屏颜色矩形 1.98 ms

无 Boss 血条时仍要扫整屏。计算受限（每像素 6 次比较，8MB 读 / 1.9ms
≈ 4.2 GB/s，比内存带宽低一个数量级）。再快只能减少扫描量
（行级跳采样、收窄区域），都会改语义，暂缓。

### D. 还没进基线覆盖的部分

- `internal/engine` 的整拍开销（截图与功能之外的部分）没有单独量，
  但它只做帧缓冲取用、功能分发、动作执行和记账，量级应在微秒级。
- ZZZ 的功能没有真实截图，无法测。
- 截图测量依赖本机有可截的窗口；CI 上会跳过。

## 口径提醒（踩过的坑）

- **模板仓库不能为空**：`NewMatcher(ocr, nil)` 会让 `MatchTemplate` 立刻报错，
  读数变成 0ms，看起来"模板匹配不要钱"。必须用 `NewTemplateStoreFS` 接真实模板。
- **量 OCR 拆分前必须设自适应 det 边长**，否则 68x57 会被放大到 960，
  det 读数 116ms（真实 8.1ms）。
- **新增 OCR 选项必须进缓存键**：`ocrCacheKey` 少一个字段就会把两次不同
  调用的结果混在一起（跳过 det 那次曾因此读数变成 3ms/114 次）。
- 绝对值随机器变化，只做同机前后对比。
- `feature.*.step` 包含该功能一帧内全部识别，会和视觉阶段重叠，不要相加。
