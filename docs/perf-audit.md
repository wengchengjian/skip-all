# 性能审计

对象：整个仓库的每帧热路径。基线数字见 [perf-baseline.md](perf-baseline.md)，
由 `scripts/perf_baseline.ps1` 在同一台机器上生成。

## 结论速览

- **基线可复现**：`pwsh -File scripts/perf_baseline.ps1` 一条命令生成
  [perf-baseline.md](perf-baseline.md)，覆盖截图 → 识别 → 决策 → 节拍四段。
- **修了 5 处**，每处都有同机前后对比（见"已修复"）：
  逐像素装箱、模板匹配滑窗、Boss 血条优先、引擎拍起点、黑屏判定提前退出。
  其中引擎拍起点那条是 bug——13ms 截图下 FPS=30 只跑到 21.3，吞吐白丢 29%。
- **否决了 3 条**，都带数据（见"已否决"）：跳过 OCR 检测、换预处理插值算法、
  模板按帧缓存。共同教训是**准确率验证比速度测量更容易被忽略**。
- **还剩两块大头**：
  截图 13ms/帧——**已查明是被显示器刷新率量化**（本机 143Hz，1x1 的屏幕回读 p50 恰好
  6.96ms ≈ 一个刷新周期）。换 DXGI Desktop Duplication 可绕开 CPU 回读，但要单独评估；
  OCR 推理 45ms/次（ONNX 算力，量化/NCNN/换模型三条路此前都已试过）。
- **稳态已经很低**：有 Boss 的战斗帧 0.083ms、剧情跳过 0.24ms。

## 方法

1. 先建可复现基线：每个阶段单独计时，并统计每次调用的分配字节与**分配次数**。
2. 分配次数比字节数更重要：字节多只是堆大，次数多才是 GC 压力的来源。
3. 单帧重复测不够——换成**真实截图序列回放**，能暴露"几十帧才跑一次"的开销。
4. 每项改动用同一脚本复测，看同机前后差。
5. **被数据否决的想法也记下来**，否则下次还会有人再试一遍。

## 一帧到底花在哪

同机（i7-13700K）实测。一段完整帧拆成"截图 + 识别 + 决策"：

| 段 | 耗时 | 说明 |
| --- | ---: | --- |
| 截图（PrintWindow 为主） | **13 ms** | 2080x1210 窗口，见下 |
| 识别（OCR + 模板匹配） | 0~45 ms | 取决于本帧是否命中缓存 |
| 决策（颜色/文字行/状态机） | 0.083~2.2 ms | 有 Boss 时 0.083ms，无 Boss 时 2.2ms |

**截图是唯一"每帧必付且无法优化"的一段**，也是整条管线的地板。

### 截图路径拆分

对着本机真实窗口量（chrome 2080x1210）：

| 阶段 | 耗时 | 占比 |
| --- | ---: | ---: |
| PrintWindow | 12.7 ms | 97% |
| BitBlt（回退，正常不触发） | 13.1 ms | — |
| 缩放 + BGRA→RGBA | 1.0 ms | 7% |
| 合计（池化路径） | 13.0 ms | 100% |

#### 为什么截图这么慢：被刷新率量化

固定开销不是常数，是**至少要等一个显示器合成帧**。对 1x1 和 1080p 各跑 120 次看分布：

| 尺寸 | min | p50 | p95 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 1x1 | 6.01 ms | **6.96 ms** | 7.56 ms | ≈ 1 个刷新周期（1/143Hz = 6.99ms） |
| 1920x1080 | 11.63 ms | **13.87 ms** | 16.01 ms | ≈ 2 个刷新周期 |

对照实验把原因钉死了：

| 操作 | 1080p 耗时 |
| --- | ---: |
| memDC → memDC（纯内存 blit） | < 1 ms |
| Go 的 `copy(8MB)` | < 1 ms |
| **屏幕 DC → memDC** | **11.1 ms** |

所以慢的不是拷贝，是**从合成后的桌面回读到 CPU**——这一次 GPU→CPU 传输
被 DWM 的合成节拍卡住。本机是 2560x1440 @ **143Hz**，显示由 Intel UHD 770 核显驱动
（另有一块无显示输出的 NVIDIA CMP 40HX）。

**结论修正**：76 FPS 不是代码的固有上限，是"这台机器 + 143Hz 刷新率"的结果。
60Hz 显示器会更差（一个周期 16.7ms），240Hz 会更好（4.2ms）。

#### 能怎么绕开

之前写的"DXGI 只能截前台所以不采用"**不准确**。DXGI Desktop Duplication /
Windows.Graphics.Capture 拿到的是合成器输出的 GPU 纹理，不需要 CPU 回读，
因此不受这个刷新率量化限制。它的约束是**窗口必须显示在屏幕上**（被遮挡或最小化就不行），
但**不需要有焦点**——这与本项目"不抢焦点"的定位并不冲突，冲突的只是
"窗口完全不可见时也能截"这一条。

这条路没有实测过，是否采用需要单独评估（实现量、驱动兼容性、权限）。

### 真实截图回放

1920x1080，38 张真实截图连续回放（每帧换图，缓存几乎不命中，比真实运行悲观）：

| 功能 | 每帧 mean | p50 | p95 | OCR 次数/耗时 | 模板次数/耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| story_skip | 9.9 ms | 5.5 ms | 27.4 ms | 4 / 135 ms | 324 / 103 ms |
| auto_combat | 33.2 ms | 10.5 ms | 147.0 ms | 17 / 915 ms | 451 / 271 ms |

要对比就看"已修复"各节里的前后差。）

## 已修复

### 1. 逐像素接口装箱（pkg/vision）

`image.Image.At()` 每次返回 `color.Color` 接口。对 `*image.RGBA` 来说，
4 字节的 `color.RGBA` 会被装箱到堆上——**每个像素一次分配**。

| 文件 | 函数 | 修前每次分配 |
| --- | --- | ---: |
| color.go | analyzeColorWith | 330,000 次 / 1.3 MB |
| textbands.go | FindTextBands | 161,202 次 / 630 KB |
| template.go | WhiteMask / grayValueAt | 22,306 次 / 303 KB |
| color.go | filterByColorRange | 随区域像素数 |

修法：`pkg/vision/pixel.go` 的 `pixelReader`，对 `*image.RGBA` 直接读 Pix。

| 阶段 | 修前 | 修后 |
| --- | --- | --- |
| vision.colorstats | 6.22 ms / 330,000 次 | 2.71 ms / 0 次 |
| vision.textbands | 1.44 ms / 161,202 次 | 0.35 ms / 2 次 |
| feature.story_skip.step | 0.94 ms / 97,174 次 | 0.21 ms / 4 次 |

### 2. 模板匹配改用列和滑动窗口

85 个内置模板里只有 1 个带掩码，所以无掩码是主路径：此时 `sumI`/`sumI2`
就是矩形窗口和，可以用列和滑动窗口 O(1) 推进，内层只剩 `sumIT` 一项。
另加一条：窗口方差过小时（纯色背景）直接跳过，省掉整趟 `sumIT`。

| 指标 | 修前 | 修后 |
| --- | ---: | ---: |
| vision.template_match（合成 48x48） | 16.75 ms | 7.93 ms（2.1x） |
| story_skip 模板总耗时 | 224 ms | 82 ms（-63%） |
| auto_combat 模板总耗时 | 485 ms | 270 ms（-44%） |

正确性：`TestMatchTemplateEquivalence` 用 24 个随机画面逐例对照优化前的
朴素实现，位置完全一致、置信度差 < 1e-9。

### 3. 战斗判定先查 Boss 血条（pkg/assist/combat）

`inCombat` 原先先查通用血条（整屏 200 万像素，约 1.9ms）再查 Boss 血条
（632x71 小矩形，约 0.04ms）。两者是"或"关系，顺序不影响结论，但代价差
两个数量级。改成先查 Boss，有 Boss 时直接短路。

| 场景 | 修前 | 修后 |
| --- | ---: | ---: |
| 带 Boss 血条的稳态帧 | 2.65 ms | **0.083 ms**（32x） |
| 无 Boss 血条的稳态帧 | 2.22 ms | 2.22 ms（无回归） |

### 4. 引擎拍起点改到截图之前（internal/engine）

`Run` 循环里 `clock.Begin` 是在 `captureFrame()` **之后**才调的，
于是实际周期 = 截图耗时 + TargetFPS 间隔，比配置的帧率慢一截——
而代码注释写的是"截图与决策的耗时被吸收进这一拍"，两者不一致。

修法：把本拍起点记在截图之前（`tickStart := time.Now()` 再 `clock.Begin(tickStart)`）。

| 配置 | 修前 | 修后 |
| --- | ---: | ---: |
| 截图 13ms，FPS=10 | 9.00 FPS（111 ms/拍） | **10.00 FPS（100 ms/拍）** |
| 截图 13ms，FPS=30 | 21.33 FPS（47 ms/拍） | **29.89 FPS（33 ms/拍）** |
| 截图 0ms，FPS=30 | 29.99 FPS | 29.99 FPS（无回归） |

截图越慢，这个 bug 吃掉的帧率越多。13ms 截图下 FPS=30 只能跑到 21.3，
等于**白白损失 29% 的吞吐**。

### 5. 颜色占比判定加提前退出（pkg/vision）

剧情跳过用 `ColorRatio` 判断"整屏是不是过场黑屏"，阈值 0.85。
原实现要把 200 万像素走完才算比例（注释里作者也记了"约 10ms"）。

新增 `ColorRatioAtLeast(img, rect, colorRange, threshold) bool`，用两条不等式中途结束：

- 命中数/总数已 ≥ threshold：后面只会更高 → true
- 即使剩下所有像素都命中也不够 → false

**数学上与原实现完全等价**（`TestColorRatioAtLeastEquivalence` 用 40 个随机画面
× 4 个阈值兜底，结论全部一致）。

| 指标 | 修前 | 修后 |
| --- | ---: | ---: |
| story_skip 每帧 mean | 12.5 ms | **9.77 ms**（-22%） |
| story_skip 每帧 p50 | 8.5 ms | **5.1 ms**（-40%） |
| 功能执行总 CPU | 2040 ms | **1750 ms**（-14%） |
| ColorRatio 占功能 CPU | 9.31% | **4.57%** |

## 已否决（有数据，别再试）

### 跳过 OCR 的文字检测（det）

det 占单次识别耗时的 60~80%（技能区 68x57：det 8.85ms / rec 2.66ms）。
实现了 `RunRecOnly` 并在 38 张真实截图上逐组对照：

| 区域 | 一致率 | 耗时比 |
| --- | ---: | ---: |
| 技能区 1（68x57） | 23.7% | 4.4x |
| 技能区 2（68x57） | 28.9% | 4.0x |
| 技能区 3（68x57） | 39.5% | 4.0x |
| 确认对话框（550x140） | 23.7% | 5.8x |
| 对话内容（960x155） | 34.2% | 2.2x |

速度快 2~6 倍，但一致率只有 24~40%。原因是 det 不只"找框"——它还会把文字
裁紧、按行归一化，rec 依赖这个规整输入。**代码已回退。**

### 把 OCR 预处理的 CatmullRom 换成 ApproxBiLinear

预处理里 `draw.CatmullRom` 在大区域上每次 2.5ms / 4MB，换成 ApproxBiLinear
只要 1ms / 0 字节。实现后逐条对照：

| 口径 | 一致率 |
| --- | ---: |
| 全部 OCR 结果 | 30.7% |
| 置信度 ≥ 0.9 的结果 | **100%（16/16）** |
| 技能冷却判定（置信度 ≥ 0.5，实际决策口径） | **28.6%（14 组）** |

高置信度结果完全一致，但 `cooldownMinConfidence = 0.5`，低置信度的乱码
也参与决策，会翻转"技能是否在冷却"。**代码已回退。**

### 给 Service.Template 加按帧缓存

回放实测模板总耗时反而从 224ms 升到 251ms——每帧换图时帧内没有重复调用，
只多付了一次像素校验和。已回退。

## 待办

### A. OCR 分配 —— 已降级为"低价值"，不建议做

OCR 每次调用分配 5.4 MB / 2,736 次，全部发生在 `third_party/go-ocr`。
本来排在待办第一位，但量了 GC 之后发现不值得：

    GODEBUG=gctrace=1 跑完整回放：GC 37 次，单次暂停 0~1ms，GC 占用 < 3%

也就是说分配**没有造成可观测的停顿或 CPU 开销**。再去做缓冲池
（还得改 third_party、同步 NOTICE）收益接近零。

换插值算法那条路也已因准确率风险否决（见上）。
**结论：OCR 分配这条线到此为止，不要再投入。**

### B. 模板调用次数偏多

auto_combat 每帧 11.9 次模板匹配、story_skip 每帧 8.5 次。
目前靠算法提速扛住了；要进一步降只能减少调用次数，会改变行为。

### C. 全屏颜色矩形 1.98 ms

无 Boss 血条时仍要扫整屏，计算受限。再快只能减少扫描量，会改语义，暂缓。

### D. 无法离线测量的部分

- **真实端到端帧率**：试过用真实功能 + 假输入跑引擎循环，但假输入不会让
  画面变化，功能会卡在"要反复点击"的状态，静止画面反而只有 2.4 FPS。
  这个数不可信，已放弃。真实帧率只能在真机上量。
- **动作执行路径**（PostMessage）：往随机窗口发按键有副作用，没有测。
- **ZZZ 功能**：没有真实截图，无法测。

## 口径提醒（踩过的坑）

- **模板仓库不能为空**：`NewMatcher(ocr, nil)` 会让 `MatchTemplate` 立刻报错，
  读数变成 0ms，看起来"模板匹配不要钱"。必须用 `NewTemplateStoreFS` 接真实模板。
- **量 OCR 拆分前必须设自适应 det 边长**，否则 68x57 会被放大到 960，
  det 读数 116ms（真实 8.1ms）。
- **新增 OCR 选项必须进缓存键**：`ocrCacheKey` 少一个字段就会把两次不同
  调用的结果混在一起（跳过 det 那次曾因此读数变成 3ms/114 次）。
- **别用假输入做端到端帧率**：动作不生效会让功能卡在重活状态，读数失真。
- 绝对值随机器变化，只做同机前后对比。
- `feature.*.step` 包含该功能一帧内全部识别，会和视觉阶段重叠，不要相加。
